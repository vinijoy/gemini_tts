# 아키텍처 연구: Gemini TTS Web UI

**조사일:** 2026-10-11  
**범위:** 기존 앱을 보존하는 Gemini 3.8 TTS 공식 기능 확장  
**신뢰도:** MEDIUM — `classify-confidence --provider context7 --verified` 실제 반환값. 공식 지원 범위와 설계 제안을 구분하며, 실제 유료 합성·청취·접근성 실기는 수행하지 않았다.

## 권장 구조

현재 `page.tsx → POST /api/tts → generateContentStream → PCM stream → PcmChunkAssembler/StreamingPcmPlayer → WAV` 경로를 유지한다. 변경은 3.8 요청 변환, 음성 자산 관리, 순차 턴 실행에 집중한다. 현재 범위에서는 데이터베이스·작업 큐·별도 서버를 추가하지 않는다.

```text
한국어 대본·화자·연출 편집 UI
  → 합성 요청 스냅샷 → /api/tts
  → 입력 검증 → 3.8 요청 변환기
  → 단일 Gemini 요청 또는 순차 턴 실행기
  → 오디오 형식 검증 → 기존 PCM 스트림·재생·WAV 저장

음성 라이브러리·설계·Remix·복제 UI
  → /api/voices 계열 서버 어댑터 → Gemini Voices API
  → 음성 식별자·수명·미리듣기 → 합성 요청에서 참조
```

## 공식 지원 범위

- 3.8은 낭독할 `text`와 연출 메타데이터를 분리한다. 스타일 지시를 대본 앞에 이어 붙이면 그대로 낭독될 수 있으므로 요청 변환기를 경계로 둔다. [S1]
- 기본 30개 음성 외에 Voice Library와 설계·복제 음성을 선택할 수 있다. 표시 이름과 API 음성 식별자를 구분하고 원격 목록을 활용한다. [S1–S3]
- 단일 요청의 `multiSpeakerVoiceConfig`는 기본 음성 최대 두 화자다. 맞춤 설계·복제 음성 대화는 턴별 합성 후 결합한다. [S1, Limitations]
- 스트리밍은 헤더 없는 24kHz·모노·16-bit little-endian PCM을 반환한다. 일반 3.8 응답과 설계 미리듣기는 WAV이므로 PCM 경로로 그대로 보내지 않는다. [S1, S2]
- `voice_...` 설계·복제 자산은 프로젝트 공유 200개 한도와 마지막 사용 후 1년 TTL이 있다. 비저장 복제의 `voicekey_...`는 7일 TTL이다. 합성 및 Remix의 기본 음성 사용은 저장 음성 TTL을 갱신한다. [S1, Custom voice limits and TTL]

## 요청과 실행 상태

앱 내부 음성 참조는 `prebuilt`, `library`, `designed`, `replicated`, `ephemeral-replica` 종류와 ID, 필요한 경우 만료 시각을 가진다. 서버 SDK 타입과 제품 입력 타입을 동일시하지 않는다. 합성 요청은 모델, 모드(`single`, `prebuilt-dialogue`, `custom-dialogue`), 화자 ID와 음성 참조, 순서가 있는 턴 배열을 가진다. 각 턴은 화자 ID·낭독 텍스트·선택적 연출을 별도 필드로 둔다.

서버에서 모델 허용 목록, 음성 ID, 화자 중복·미등록 화자, 텍스트 길이, 모드와 음성 종류의 조합을 검증한다. 기존 1,000자 제품 제한을 모델의 토큰 한도와 혼동하지 않는다. 대화에서는 전체 대본 제한과 턴별 제한을 명시해 요청 분할로 제한이 우회되지 않게 한다.

생성 시작 시 요청 스냅샷과 `runId`를 고정한다. 편집 중인 값이 진행 중 요청에 섞이지 않게 한다. 상태는 `idle → preparing → streaming → complete`, 별도 종료 상태 `cancelled/failed`로 둔다. 마지막 턴까지 정상 종료해야 전체 완료다.

## 데이터 흐름

### 단일 음성과 기본 두 화자

UI 요청 → 서버 검증 → 3.8 요청 변환 → 기존 재시도·취소 범위에서 Gemini 스트림 → PCM 형식 검증 → 기존 바이트 스트림 → 기존 청크 조립과 재생 → 정상 완료 후 WAV. 기본 두 화자는 대본의 화자 ID가 설정된 음성과 정확히 대응해야 한다. 알 수 없는 화자를 조용히 기본 음성으로 치환하지 않는다.

### 음성 라이브러리·설계·Remix·복제

서버 Voices 어댑터를 단일 통로로 사용한다. 브라우저에 API 키를 전달하지 않는다. 목록은 원격 자산 상태를 기준으로 하며 짧은 캐시와 새로고침을 제공한다. 만료되거나 삭제된 음성은 명시적인 재선택 상태로 돌린다.

- **라이브러리:** API ID·표시 이름·종류를 정규화해 검색·선택에 사용한다. 필터·페이지 처리는 실제 API 스키마를 따른다.
- **설계:** 설명 → `type="prompted"` 생성 → `voice_...` ID와 WAV 미리듣기 → 선택. 자산 생성 실패와 미리듣기 재생 실패를 구분한다. [S1, S2]
- **Remix:** 기본 음성 참조와 변경 설명을 별도로 받고 새 자산 결과를 확인한 뒤 선택한다. 본 연구에서 확인한 문서는 TTL 갱신을 명시하지만 정확한 요청 필드는 입증하지 못했다. FEATURES 담당 연구의 공식 Voices API 스키마를 채택하며 추정 필드를 구현하지 않는다.
- **복제:** 참고 음성과 동의 음성을 별도 입력으로 검증하고 `type="replicated"`로 생성한다. 저장형과 비저장형의 수명을 구분한다. 업로드 원본을 기본적으로 앱 서버에 영구 보관하거나 일반 로그에 기록하지 않는다. [S1, S3]

설계·복제·Remix는 자산 생성 부작용이 있으므로 합성용 재시도 정책을 그대로 복사하지 않는다. 응답을 잃었을 때 생성 여부를 확인할 방법을 먼저 마련한다. 공식 idempotency 지원은 이 연구에서 확인하지 못했다.

### 맞춤 목소리 여러 턴

턴 배열을 순서대로 실행하고 각각 해당 음성으로 합성한다. 초기 구현은 하나의 브라우저 요청 안에서 서버가 순차 실행하는 구조로 충분하다. 병렬 생성은 완료 순서·메모리·취소 복잡도를 늘리므로 도입하지 않는다.

각 턴에서 기존 `generateContentStream` PCM 경로를 재사용한다. 모든 턴의 형식이 같음을 확인하고 PCM 프레임만 순서대로 전달한다. 첫 턴의 첫 청크부터 재생하며 마지막 턴 완료 후 한 개의 WAV를 만든다. 턴 사이 여백을 제공한다면 명시적 제품 설정에 따라 무음 샘플을 추가한다. 자연스러운 연결·발음·운율은 실제 청취 수용 대상이다.

WAV 파일 전체를 바이트로 연결하지 않는다. 일반 응답이 필요하다면 RIFF 구조와 data 청크를 파싱한다. 모든 WAV가 44바이트 헤더라고 가정해 자르는 구현은 피한다. 스트리밍 PCM을 유지하면 컨테이너 파싱 없이 기존 조립기를 쓸 수 있다. [S1]

## 유지할 계약과 회귀 확인

| 계약 | 적용 원칙 | 회귀 시나리오 |
|---|---|---|
| 첫 PCM 재생 | 전체 파일을 기다리지 않음 | 첫 청크, 네트워크 지연 |
| 전체 취소 | 현재 요청·재시도 대기·다음 턴을 동일 실행 신호로 제어 | 대기 중·턴 사이 취소, 늦게 도착한 청크 |
| 제한적 429 재시도 | 기존 횟수·대기 유지, 사용자에게 PCM 전송 후 전체 실행 재시도 금지 | 첫 PCM 전후 429, 일부 턴 뒤 실패 |
| 중간 실패 | 부분 결과를 완성본으로 표시·저장하지 않음 | 뒤 턴 실패 시 앞 턴 중복 재생 방지 |
| PCM 형식 | 24kHz·모노·PCM16LE 및 청크 경계 유지 | 홀수 바이트, 다른 MIME/rate, 빈 오디오 |
| 완료 증거 | 정상 종료와 모든 턴 완료를 확인 | 비정상 finishReason, 마지막 턴 누락 |
| 정리 | 기존 재생기 직렬 정리 사용 | 연속 생성, 취소 후 재생, object URL 해제 |

초기 여러 턴 기능은 전체 실행 기준 첫 PCM 이후 자동 재시도를 금지한다. 나중에 턴별 중복 방지 경계를 증명하면 아직 외부로 전송하지 않은 턴만 재시도하는 정책을 추가할 수 있다. raw PCM 중간에 진행 JSON을 끼워 넣지 않는다. 별도 이벤트 채널은 필요가 확인될 때 명시적 프로토콜 변경으로 도입한다.

## 피해야 할 구조

- 기능마다 다른 재생기: PCM·정리·취소 검증이 중복된다. 공통 PCM 경로를 유지한다.
- 모든 음성을 단일 두 화자 설정에 넣기: 공식 지원 차이가 숨겨진다. 모드에 따라 단일 요청과 순차 턴을 분기한다.
- WAV 미리듣기를 PCM 재생기에 넣기: 헤더 소음·길이 오류가 생긴다. 완성 Blob 재생 경로를 쓴다.
- 자산 생성 실패의 무조건 재시도: 중복 생성과 한도 소모가 가능하다. 결과 확인 경계를 둔다.

## 구현 순서와 확장

1. 3.8 텍스트/연출 분리, 모델·음성 필드, PCM와 실패 판정 회귀 검증.
2. 기본 음성·두 화자 편집과 접근성 검증.
3. 확장 라이브러리·설계 및 스키마가 확인된 Remix·복제, 자산 수명과 서버 경계.
4. 같은 자산 참조 모델을 이용한 맞춤 여러 턴, 중간 실패·전체 취소 검증.
5. 실제 한국어 음성·두 화자 구별·키보드/VoiceOver·재생과 다운로드 일치 수용.

확장 시에는 먼저 프로젝트 쿼터·동시 스트림 수·메모리·호스팅 요청 시간 한도를 측정한다. 백그라운드 장문 작업이나 여러 사용자의 자산 격리 요구가 생기면 영속 작업·접근 제어·저장소를 도입한다. 사용자 수만으로 데이터베이스와 큐를 미리 넣지 않는다.
